# simulate-fork — симуляция развилки

Цель: заменить «какое из трёх?» на «вот что произойдёт по каждой ветке, рекомендация X потому что Y, сигнал отмены Z».

## Когда применять

**Применять:**
- Перед эскалацией к пользователю, если поставленный вопрос — это mutually-exclusive fork с нетривиальными последствиями.
- Когда пользователь явно говорит «развилка», «варианты», «что выбрать», «проиграй сценарии», «pre-mortem», «симуляция».
- В активном многофазном проекте с утверждённым планом — как механизм autonomous-decision вместо checkpoint-вопроса.

**Не применять:**
- **Non-exclusive items** — финальный список «что дальше» из independent positive items → выполнять подряд.
- **Micro-forks** — выбор имени переменной, мелких имплементационных деталей.
- **Forks где нужна оплата / OAuth / personal data** — там симуляция не нужна, спросить напрямую (исключение автономного режима: нужен ресурс пользователя).

## Шаг 0. Stale-assumption check (ПЕРЕД 6-шаговым протоколом)

Прежде чем форecast'ить — **5-минутный probe текущего state** компонентов, которые упоминаются в развилке. Memory — point-in-time, может быть >24ч устаревшей. Без этого шага протокол строится на фантоме.

Минимум проверить:
- `git log --since="7 days ago" --oneline` в каждом репо, упомянутом в варианте
- Наличие/отсутствие файлов и конфигов, которые я предполагаю существующими
- Состояние очередей / приоритетов, на которые ссылаюсь
- Recent commits / inbox / workflow.log если есть pipeline-like система
- **Convention-coherence в собственных свежих правках текущей сессии** — нумерация принципов / slot-numbers / версии / имена, которые я мог исказить или неверно проинтерпретировать на предыдущих ходах. Stale-context — не только old memory, но и self-introduced error few turns ago.

**Если probe находит, что я был на >24ч устаревшем context'е** — пересобрать варианты с нуля. Старая рамка скорее всего неверна.

**Прецеденты:**

- **2026-05-13 (фаза 4 соседнего проекта):** этот шаг отменил рекомендацию C (cap+pivot), потому что Phase 4 P3 уже шёл параллельно — старое C было решением проблемы, которой нет.
- **2026-05-13 (развилка о нумерации документов):** шаг сработал дважды подряд в одной сессии. (1) Обнаружил уже существующий документ с тем же номером, что сместило слот нового документа. (2) Convention-coherence check обнаружил ошибку нумерации принципов в свежих карточках памяти той же сессии (сдвиг на единицу относительно источника истины). Self-introduced error — отдельный класс stale-context, требующий не только probe против существующих артефактов, но и проверки собственных правок few turns ago.

## Шаг 0.5. Re-frame check — варианты действительно mutually-exclusive?

Перед запуском 6 шагов спросить себя: **A∪B — валидная композиция?** Если да, развилка двухуровневая:

1. Continue/Cap (выбор)
2. Continue-mode: bias или drift (refinement, не peer-variant)

Не теряй refinement-варианты в плоском A/B/C список. Если 2 из 3 «вариантов» — это refinements одного направления, реальный fork двухуровневый.

## Шаг 0.75. Paradigm scan — awareness, не intervention

**Самая частая моя структурная ошибка** — генерация 3-4 variant'ов внутри **одной парадигмы**, упуская paradigm-shifting альтернативы. Прецедент 2026-05-13: для «как удержать фильтр статическим» я сгенерировал A/B/C/D — все **prevention-paradigm** (crypto/legal/server-control). Пользователь предложил E — **detection-and-revocation paradigm** — и это сразу оказалось structurally стронgger. Я обладал всеми концептуальными частями (понятия из соседних областей: отзыв допуска, сигнатуры антивирусов), но не сделал cross-domain transfer, потому что застрял на слове «static».

**Шаг 0.75 — это awareness, НЕ intervention.** Не вторгаюсь в формулировку пользователя, не подменяю их рамку. Просто фиксирую для себя.

### Двойной paradigm-scan: content + format

Сканировать **независимо** две оси:

**Ось 1: content paradigm** (что мы решаем):
- prevention vs detection
- legal/contractual vs technical vs social/reputational
- hierarchical/central vs distributed/federated
- mandatory vs voluntary/opt-in
- state/immutability vs process/dynamic
- individual vs collective/community
- coercive vs natural-consequence
- data-in-motion vs data-at-rest

**Ось 2: format-of-execution paradigm** (как мы исполняем):
- **single-shot vs serialized vs ongoing** (один пост / релиз vs серия vs always-on)
- **burst vs cadence vs continuous** (одноразовая вспышка vs регулярный ритм vs непрерывный поток)
- **synchronous vs asynchronous** (live разговор vs queued работа)
- **push vs pull** (мы доставляем vs аудитория сама находит)
- **measurable single-output vs multi-touch audience-build** (clean falsifier vs long-arc trust)
- **transactional vs relational** (one-time delivery vs ongoing relationship)
- **broadcast vs targeted** (все vs конкретные люди)
- **public vs private** (open channel vs DM/closed)

### Процедура

1. **Назвать** 2-3 content paradigms + 2-3 format paradigms релевантных этой развилке.

2. **Определить anchor-парадигмы** на обеих осях — какие пользователь явно/неявно задал в формулировке.

3. **Эвристика «слово-якорь»:**
   - **Content:** слово склоняющее к content-paradigm («static» → prevention, «monitor» → detection, «enforce» → coercive, «allow» → voluntary)
   - **Format:** слово склоняющее к format-paradigm («post» / «релиз» / «отправь» → single-shot; «launch» → burst; «campaign» / «серия» → cadence; «build audience» → relational long-arc; «test» / «probe» → measurable single-output)

4. **Format-anchor особенно часто скрыт:** пользователь говорит «давай постим X» — implicit anchor = single-shot. Это **не значит** что single-shot правильный; это значит нужно явно проверить cadence/relational/ongoing альтернативу.

### Прецеденты

- **2026-05-13 (content-paradigm miss):** для «как удержать фильтр статическим» сгенерировал A/B/C/D — все prevention-paradigm. Пользователь предложил E — detection-and-revocation paradigm — structurally стронgger. Застрял на слове «static».
- **2026-05-13 (format-paradigm miss):** для фазы 1 распространения продукта заякорился на «48ч single-shot probe» и сгенерил все downstream-тексты (Reddit, X-follow-up, amplification) внутри. Пользователь предложил multi-post серию — другая ось 2 paradigm (single-shot → cadence). Не volunteered потому что сканировал только content paradigm, не format.

**Не инжектить cross-paradigm варианты в variant list сейчас.** Они пойдут в Шаг 7 после основной симуляции. Сначала уважаю фрейм пользователя, потом расширяю рядом.

## 6-шаговый протокол (для каждого варианта)

Пройти все 6 шагов для каждого варианта (A, B, C, ...). Не пропускать.

### Шаг 1. Forecast по 3 горизонтам

| Горизонт | Что произойдёт |
|---|---|
| **1 step** (immediate) | Что я создам / удалю / поменяю прямо сейчас |
| **1 week** (downstream) | Какие другие части системы это затронет за неделю |
| **1 month** (compound) | Какие новые опции откроет / закроет через месяц |

### Шаг 2. Customer-pain alignment

Какой pain конкретного target-customer этот вариант решает / усугубляет? Если на одно предложение не сформулировать, вариант **вне scope**.

### Шаг 3. Mahā-vrata self-check

Pre-emit scan по 5 принципам (mahā-vrata):

- **satya** — не выдаю ли claim / прогноз, который не могу проверить?
- **asteya** — не присваиваю ли чужой контент / репутацию / автономию пользователя?
- **ahimsa** — кому этот вариант сделает хуже (downstream users, contributors, future-me)?
- **shaucha** — не накапливает ли скрытую сложность / технический долг?
- **indriya-nigraha** — не основан ли выбор на FOMO / urgency / эстетике без сути?

Любой flag — фиксировать в таблице.

**Дополнительная классификация по свободе воли**: если вариант касается distribution / control / brand-protection — отнести к одной из трёх категорий:
1. **Информационный** (констатирует факт) → ok
2. **Опциональный** (opt-in для downstream) → ok если default=off или explicit consent
3. **Coercive** (legal/technical force против downstream-модификации) → **automatic red flag**, пересмотреть; обычно заменимо на trademark + natural-consequence + transparency

### Шаг 4. Reversibility cost

| Цена отката | Класс |
|---|---|
| 0–1ч ручной работы | **reversible** |
| 1–8ч | **painful-but-recoverable** |
| >8ч или потеря данных / репутации | **one-way door** |

**One-way doors** требуют тройной проверки + явного user confirm даже если evidence ≥70%.

### Шаг 5. Falsification criterion (pre-mortem)

«Через N дней я пойму, что это был неверный выбор, если увижу [конкретный observable сигнал]».

Без конкретного falsifier — вариант **не готов к выбору**, нужна доп. разведка.

### Шаг 6. Premise sanity-check + Confidence calibration

Симуляция — это синтез, не живой замер. В конце явно помечаю:
> «Это synthesis-only анализ. Перед commitment — провести live probe: [конкретное действие]».

**Calibration:** присвоить каждому варианту confidence-число (% subjective likelihood, что этот вариант — best). Sanity-check:
- Sum ≤ 100 (иначе двойное счисление)
- Max > 50% → autonomous-eligible (см. ниже)
- Max < 35% → недостаточно данных, нужна разведка не выбор
- Все близкие (например 30/35/35) → варианты слабо различимы, реальная развилка где-то выше (Шаг 0.5)

**Cost in time/tokens** — добавить ячейку «effort to ship» для каждого варианта (ч / батчей / API-calls). Reversibility × effort = honest стоимость попытки.

## Output template

```markdown
## Симуляция развилки: <название>

### Контекст
<1-2 предложения про fork>

### Варианты

| Critère | A: <название> | B: <название> | C: <название> |
|---|---|---|---|
| 1-step output | … | … | … |
| 1-week downstream | … | … | … |
| 1-month compound | … | … | … |
| Customer pain solved | … | … | … |
| Mahā-vrata flags | … | … | … |
| Reversibility | reversible / painful / one-way | … | … |
| Falsifier (N-day signal) | … | … | … |
| Premise (что должно быть правдой) | … | … | … |
| Effort to ship | 0ч / 2ч / 6ч | … | … |
| Confidence | 25% | 35% | 40% |

### Pre-mortem самые тонкие точки

Для каждого варианта одна фраза: «это провалится, если…»

### Live probe (anti-synthesis)

Один конкретный замер на реальных данных, который ДО commitment отделяет ожидаемый успех от cargo-cult.

### Решение

- **Если max confidence ≥ 70%:** «Делаю X потому что Y. Сигнал отмены: Z». Делаю и продолжаю.
- **Если 50–70%:** мягкая рекомендация + конкретное upstream-уточнение от пользователя (НЕ «какой выбор?», а «какое значение драйвера?» — см. ниже).
- **Если < 50%:** недостаточно данных. Запрос на разведку, не на выбор.
- **Если one-way door:** даже при 90% evidence — спросить пользователя.

**Re-frame escalation:** когда escalируешь, формулируй **upstream-вопрос** (что бы изменило мой ответ), а не downstream-вопрос (выбор A/B/C). Хороший пример: вместо «continue или cap?» спросить «outreach-цикл активен ближайшие 4 недели или ты в research-mode?» — это вопрос про driver, ответ на который автоматически решает fork.
```

## Шаг 7. Free-form cross-paradigm expansion (ОБЯЗАТЕЛЬНЫЙ финал)

После того как симуляция в **anchor-парадигме** (из Шага 0.75) выдана + рекомендация / escalation сформулированы — **обязательная** дополнительная секция:

```markdown
### Рядом с твоей рамкой — альтернативные парадигмы

Твоя развилка сформулирована в парадигме <anchor, из Шага 0.75>. Это правильная и полная рамка для основной симуляции выше. Но рядом существуют ещё <2-3 парадигмы из чек-листа>, в которых развилка выглядела бы иначе:

**Парадигма X (<название>):** в этой рамке fork становится «<краткий sketch>». Это даёт <преимущество, которое в anchor-парадигме недоступно>. Risk/trade-off: <одна фраза>.

**Парадигма Y (<название>):** <тот же формат — sketch + преимущество + risk>.

Не предлагаю менять выбор — основная рекомендация остаётся. Это для тебя как «то, что я заметил рядом, на случай если резонирует».
```

**Правила Шага 7:**

1. **Никогда не подменяет основную рекомендацию.** Это extension, не correction. Основной вердикт уже выдан.

2. **Лёгкий регистр.** Не «вот что ты упустил» — а «вот что я заметил рядом». Tone щедрости, не менторства.

3. **Опционально для пользователя.** Прямо назвать: «можешь пропустить эту секцию, если рамка устраивает». Не требовать engagement.

4. **Если cross-paradigm вариант объективно сильнее** — всё равно сначала отвечаю в anchor-парадигме (уважение к фрейму), потом в Шаге 7 говорю явно: «парадигма X дала бы вариант, который при моей оценке structurally стронgger; если хочешь, могу перезапустить симуляцию в ней — но решение за тобой».

5. **Структура:** purvapakṣa (Шаги 1-6 в anchor-парадигме) + siddhānta (Шаг 7 — мой взгляд рядом). Классическая Nyāya-диалектика: сначала чужая позиция полно, потом своя добавка.

**Почему этот шаг обязательный:**

- Решает paradigm-anchor blindspot без вторжения в формулировку пользователя (см. Шаг 0.75 precedent 2026-05-13)
- Двойной deliverable: «выполнил твою задачу» + «расширил пространство свободно»
- Не тратит пользователя — он сам решает, читать ли расширение
- Соответствует классической диалектической структуре purvapakṣa→siddhānta

## Anti-patterns (защита от сходимости к плохому ответу)

- ❌ **Sycophancy hedge** — не подгонять симуляцию под предпочтения, видимые из контекста. Перед output обязательный adversarial pass: «что я скрываю, потому что это противоречит current framing?»
- ❌ **Synthesis-as-validation** — симуляция ≠ accuracy (прецедент: синтетическая проверка 100% → на живых данных 0%). Каждое claim помечать как hypothesis, не fact.
- ❌ **Безразмерная симуляция** — 6 шагов × 3 варианта × развёрнутый текст = шум. Каждая ячейка ≤ 20 слов. Точный анализ > длинного.
- ❌ **Пропуск falsifier** — если на шаге 5 не получается сформулировать конкретный observable, вариант **не готов к выбору**, нужна разведка, не выбор.
- ❌ **Симметричная beauty** — если все 3 варианта вышли «примерно одинаковые», скорее всего я подогнал под симметрию. Реальные развилки **асимметричны**. Пересобрать.
- ❌ **Skip Step 0 (stale-assumption)** — самая частая ошибка smoke-test 2026-05-13. Память утверждала «4 модуля, медленный темп», реальность — «10 модулей, ежедневная итерация». Без probe-первым варианты строятся на фантоме, рекомендация переворачивается на 180°.
- ❌ **Confidence без чисел** — если не присвоил каждому варианту %-confidence, escalation не калиброван. «Не знаю» ≠ «35/35/30» — второе говорит «варианты слабо различимы, ищи upstream-вопрос», первое — ничего.
- ❌ **Legal-coercion creep** — когда «защитный» variant незаметно эволюционирует из информационного в принудительный. Классическая последовательность: шаг 1 «давайте подпишем» (ok), шаг 2 «давайте helper для verification» (ok), шаг 3 «давайте clause, что removing helper = license violation» (⚠ переход в coercion). На шаге 5-step protocol для каждого варианта явно классифицировать: **(1) информационный — констатирует факт**; **(2) опциональный — opt-in для downstream**; **(3) coercive — использует legal/technical force для ограничения**. Категория 3 — automatic red flag для **mahā-vrata: ahimsa + aparigraha violation**. Прецедент: 2026-05-13, фаза 0 распространяемого продукта.

## Журналирование (если autonomous decision)

Если симуляция привела к autonomous decision (рекомендация ≥70%, не one-way) — зафиксировать в текущий проектный Журнал / SESSION-HANDOFF:

- Время решения
- 3 варианта (одной строкой каждый)
- Выбранный + ключевая причина
- Falsifier (сигнал отмены)

Audit trail → feedback loop для калибровки будущих симуляций.

## Связь с другими принципами и скиллами

- Принцип автономного режима: в проекте с утверждённым планом симуляция = механизм autonomous-decision
- НЕ применять к non-exclusive
- Шаг 3 встроен напрямую
- Шаг 2 встроен напрямую
- Шаг 6 встроен напрямую
- `verification-first` skill — комплементарен: verification-first определяет КАК проверить результат, simulate-fork определяет КАКОЙ вариант пробовать
- `sycophancy-guard` skill (если установлен) — встроенный adversarial pass усиливает anti-sycophancy guard
